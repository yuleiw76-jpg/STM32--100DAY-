## 2. 工具分工与理解修正

CubeMX是图形化配置和初始化工程生成工具。本节用它生成基于HAL的工程，不是点击外设后就能自动生成所有业务逻辑。

HAL是驱动代码，通常按STM32系列提供；F103使用STM32F1系列HAL，并非每个具体料号都完全独立一套库。Keil是工程编辑、构建、下载与调试环境，既能开发标准库工程，也能开发HAL工程。

用户最初把Keil理解为“什么都必须自己配置”，经解释明确了新流程：CubeMX生成初始化与工程框架，再在Keil补应用逻辑、构建及下载。随后“只写一个main函数即可”的理解也作了限定：简单闪灯可以主要在生成的main.c中补代码，但工程仍包含驱动、启动、中断、系统时钟等文件；复杂项目仍需自己组织其他函数与模块。

这一分工已经讲解与纠正，未把它扩展成用户已独立建立任意复杂HAL工程。

## 3. 时钟知识与问答结果

### 四种来源与外部模式

- H/L表示高速/低速，E/I表示外部/内部，用户能解释这些缩写。
- HSE本例按板上8MHz无源晶振使用；HSI来自芯片内部RC，不能只因都涉及8MHz就当作同一种来源。
- LSE通常用32.768kHz外部晶振为RTC提供时钟；LSI约40kHz，可用于独立看门狗IWDG，也可用于RTC。四种都是时钟源，低速不能笼统等同于“备用时钟”。
- Crystal/Ceramic Resonator配合无源晶振或陶瓷谐振器；Bypass接收外部已经产生好的时钟信号，来源也可以是其他芯片，不只限于单独有源振荡器。

用户能根据自己的无源晶振选择HSE的Crystal/Ceramic Resonator。HSE与LSE必须分别按硬件判断，不能因一个使用外部晶振就把另一个也开启。

### 8MHz到72MHz主路径

用户自行说明了主线：HSE不分频进入PLL，9倍频得到72MHz，作为系统时钟，再经AHB的1分频到达HCLK。

```text
HSE 8MHz → 预分频1 → PLL ×9 → PLLCLK 72MHz
SYSCLK选择PLLCLK → AHB ÷1 → HCLK 72MHz
```

补充强调：SYSCLK选择PLLCLK是独立选择动作，不是打开PLL就自动换成PLL作为系统时钟。这里的×9是倍频，不是电压幅度放大。

### APB总线与定时器计数时钟

用户此前知道TIM1挂APB2，TIM2/3/4挂APB1，但CubeMX图只写APB1/2 timer clocks，没有逐个列出TIM编号；两者并不矛盾。

对这里的F103定时器：对应APB预分频为1时，定时器输入时钟等于PCLK；对应APB预分频不为1时，为PCLK的2倍。之后才进入定时器自己的PSC。

用户第一次把HCLK=72MHz、APB1四分频情况下的TIM2时钟答成18MHz。解释后明确18MHz是PCLK1，TIM2时钟应为36MHz。随后能正确回答：APB1八分频时，PCLK1=9MHz、TIM2在PSC之前为18MHz。

```text
PCLK1 = HCLK / APB1分频系数
定时器时钟 = PCLK1 ×（APB1分频为1时取1，否则取2）
CNT计数频率 = 定时器时钟 / (PSC + 1)
```

不能把“×2”记成无条件规则，也不能把APB预分频与定时器PSC混为一谈。HCLK=72MHz时，APB1不能用1分频超出其36MHz上限。

### SysTick不是APB2上的TIM外设

SysTick是Cortex-M3内核自带的24位向下计数器，不是TIM1～TIM4之一，也不挂APB1或APB2。昨天的TIM2配置成向上计数，但TIM2本身并非只能向上计数。

用户最初误认为SysTick在APB2上，并认为改变APB2分频就会改变其计数速度。解释时把时钟树拆成并行分支：

```text
HCLK
├─ SysTick时钟支路
└─ APB2分频 → PCLK2
```

在HCLK与SysTick自身设置不变的前提下，仅修改APB2分频改变PCLK2，不改变SysTick计数速度。用户最后正确指出改变的是PCLK2；这不等于已经对所有SysTick时钟选择和重装载问题做了独立复测，后续仍可短时复习。

旧标准库例程的delay_ms/delay_us使用SysTick，但不能据此把旧delay.c直接搬入HAL工程。作为本次源码核对补充：当前默认HAL_InitTick建立毫秒时基，SysTick_Handler调用HAL_IncTick，HAL_Delay等待时基累计；不把旧例程的轮询寄存器实现与HAL实现完全等同。

## 4. 当前工程与应用代码

当前main的主要调用顺序为：HAL_Init → SystemClock_Config → MX_GPIO_Init → while(1)。HAL_Init负责HAL基础初始化及默认时基等工作；不是要求用户从头重写整套启动框架。

应用代码位于USER CODE区域：

```c
HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, GPIO_PIN_RESET);
HAL_Delay(800);
HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, GPIO_PIN_SET);
HAL_Delay(800);
```

800是HAL_Delay的毫秒参数，两段相加形成标称约1.6秒的一轮逻辑，不是仪器测得的精确周期。GPIO_PIN_RESET/SET表示输出低/高电平；亮灭对应关系由板载LED接法决定，不能说所有LED都是RESET点亮。

当前gpio.c核对结果：PC13推挽输出、无上下拉、GPIO_SPEED_FREQ_LOW，初始输出RESET。PC13不能机械照抄“输出速度一律选最高”的说法；ST数据手册对PC13～PC15的输出速度与驱动能力有特殊限制。本次源码已经使用LOW，没有为收尾修改它。

当前SystemClock_Config使用HSE_ON、HSE预分频1、PLL乘9、AHB分频1、APB1分频2、APB2分频1，未主动开启LSE。保存的.ioc仍有PC14/PC15的LSE引脚角色，记录这一现状，不据此单独判定LSE实际工作或擅自改写配置。重新生成后的源码应再核对。

手册中MCO引脚PA10为笔误：本器件MCO为PA8。本次不使用MCO。未启用ADC、USB等外设，不把时钟树中未使用分支的显示值当作已完成相应外设实验。

## 5. 调试记录

### A. CubeMX缺少F1固件包

- 现象：Generate Code要求STM32Cube FW_F1 V1.8.7或依赖包。
- 假设：未安装该版本、安装了其他包，或仓库路径不匹配。
- 测试：检查默认仓库与用户包管理器截图。
- 观察：默认仓库当时没有F1包目录，用户明确说一个都没下载。
- 结论：当时确实缺少F1固件包，不能把Keil设备支持包当作CubeMX固件包。
- 修改：指导用户在官方流程中登录自己的myST账号、选择需要的版本并继续安装；助手不处理账号密码和验证码。
- 验证：后续工程使用FW_F1 V1.8.7生成并能完成构建、实物运行。本次不把软件包完整性验证扩大为所有工具版本均已测试兼容。

### B. Keil链接错误L6236E

- 现象：led.sct第7行报No section matches selector，无法产生目标程序。
- 假设：要求置首的RESET段没有对应输入目标文件。
- 测试：核对工程文件列表、启动文件内容和构建输出。
- 观察：startup_stm32f103xb.s在MDK-ARM目录中，内含AREA RESET；当时.uvprojx没有它的文件引用，也没有相应汇编记录。
- 结论：启动文件没有参与构建，是这次链接失败的直接原因。打开文件不等于把文件加入工程。
- 修改：用户通过Add Existing Files to Group补入现成文件；当前保存在Drivers/STM32F1xx_HAL_Driver分组中。分组名称是组织方式，不改变它作为启动文件的作用。
- 验证：当前工程引用该文件，成功日志包含assembling startup_stm32f103xb.s，最终0错误、0警告。

不要删除链接脚本里的RESET置首要求来掩盖问题。正常CubeMX工程应自动带上启动文件与引用，同一工程保存后不需每次构建都重加。再次生成会更新工程配置，需复查手动修复是否被保留。

### C. Utilities界面与手册不同

- 现象：用户看到Use Debug Driver，而不是手册独立选择J-Link的下拉框。
- 核对：用户勾选该选项，手册没有勾选。
- 结论：勾选时Flash编程沿用Debug页的驱动；取消时可独立指定。它不是前述链接错误的原因，也不要求界面与手册每个勾选都一致。

### D. J-Link找不到JTAG链中的Cortex-M

- 现象：No Cortex-M Device found in JTAG chain，之后Flash Download failed / Target DLL has been cancelled。
- 假设：下载器接口模式与实际接线不匹配。
- 测试：读取截图日志中的JTAG selected和Scanning JTAG chain failed。
- 观察：当前使用SWD接线，但下载器选择了JTAG。
- 修改：指导用户把J-Link Settings中的Port改为SW，并确认Utilities是否沿用同一设置。
- 验证：用户报告改好后LED能够正常亮灭，并提供实物照片。

第二个下载取消提示是连接失败后的结果，不是DLL文件损坏的证明。CubeMX的Serial Wire配置芯片端，Keil的Port配置下载器端，两边需要匹配。
