## 数据路径与接线

本程序的主路径如下，不是三个串口各自直接连到电脑：

```text
printf → USART3_TX（PB10）
          ↓ 杜邦线
        USART1_RX（PA10）→ 接收中断 → USART1_RX_BUF
          ↓ 主循环复制并补回车换行
        UART2_Send_String → USART2_TX（PA2）
          ↓ USB转TTL模块的RX → USB → 电脑XCOM
```

以下是手册接线表与当前工程默认引脚配置的对应，不是对实物每条线的独立测量：

| 连接 | 作用 |
| --- | --- |
| USB转TTL模块 GND ↔ 单片机 GND | 共地 |
| 模块 TX ↔ PA3（USART2_RX） | 电脑向串口2发送；本次主路径未使用此方向 |
| 模块 RX ↔ PA2（USART2_TX） | 串口2向电脑发送 |
| PB10（USART3_TX）↔ PA10（USART1_RX） | 串口3发送给串口1 |
| PA9（USART1_TX）↔ PB11（USART3_RX） | 反向连接；本次主路径未使用此方向 |
| 模块 USB ↔ 电脑 USB | 电脑串口接口 |

改线应先断电；TX 接对端 RX。电源连接与模块电平应另行确认，不能把接线表没有列出 VCC 理解为任何供电方式都可用。

## 代码与知识对应

| 知识单元 | 当前工程及理解 |
| --- | --- |
| 初始化 | `uart_init(115200)`、`uart2_init(115200)`、`uart3_init(115200)`；本实验串口设置为115200、8N1 |
| 发送分工 | 本工程重定向的 `fputc` 写 `USART3->DR`，所以 `printf` 经串口3发送；`UART2_Send_String` 经串口2发送 |
| 接收资源 | 每个串口各有自己的 `STA` 与 `BUF`；共同使用 `USART_REC_LEN=200` 容量常量，不是共用同一块缓冲区 |
| 完成标志 | `STA` 的 bit15 标记接收完成，bit14 标记已收到 `\r`，低14位记录有效字节数 |
| 字符串拼接 | `strcat(text,"\r\n")` 从已有字符串的 `\0` 处追加回车换行，再写新的 `\0` |
| 字符串容量 | `text[20]` 如需追加 `\r\n` 和 `\0`，最多容纳17个正文数据字节；`strcat` 本身不保护容量 |
| 总线时钟 | USART1 属于 APB2；USART2、USART3 属于 APB1；GPIOA、GPIOB 属于 APB2 |

同一总线的使能可以把多个标志用 `|` 合并，也可以分开调用。不同总线必须用各自的时钟使能函数，不能只为了写法统一而放到同一个调用里。

`\r\n` 是本例约定的一条消息结束标记；`\0` 是 C 字符串结束标记。接收状态机不把回车换行保存为正文，转发时才重新追加。两者不能混为一谈。

## 补充知识：优先级和延时

抢占优先级决定一个中断能否打断另一个中断；相同抢占优先级不能相互抢占。子优先级用于同组中断同时处于等待状态时的处理次序，不是抢占权限。上述解释以正确配置优先级分组为前提。[ST Cortex-M3 编程手册](https://www.st.com/resource/en/programming_manual/CD00228163-.pdf#page=36)

本工程填写的三个优先级字段分别是0/0、0/1、0/2，但未在应用代码中找到显式设置优先级分组的调用。因此这里只记录字段值，不把它们当成已经验证的实际抢占或等待排序。

`fputc` 在写当前字符之前等待串口3的 TC 标志。因此最后一个字符写入后，`printf` 返回不等于最后一字节已在线上传完。115200、8N1 时，一字节占10个位时间，约86.8微秒；`delay_us(200)` 给末尾传输、接收中断和主循环处理留出时间。200微秒是例程的安排，不是所有程序的通用保证。[ST STM32F1 参考手册](https://www.st.com/resource/en/reference_manual/cd00171190.pdf)

### 本次复习纠正：为什么新字符不会进入 BUF？

假设 bit15 已是1，而主循环尚未清零，新字节到来时，中断仍可以执行并读取到 `Res`。但接收处理要求：

```c
if ((USART1_RX_STA & 0x8000) == 0)
```

bit15=1 使这个条件不成立，新字节不会写进 `BUF`。原因是完成标志的门控，不是 `delay_us()` 禁止接收；当前延时函数没有关闭接收中断。即使去掉延时，在该标志仍为1的这段时间，新字节仍会被这段软件忽略。

## 原工程保留的注意项

1. `USER/main.c` 仍声明 `u32 a;`，没有初始化就用于输出和递增。应初始化（例如 `u32 a = 0;`）；当前起始数值不能解释成可靠的从零计数。本次归档没有擅自修改。
2. `strcpy` 和 `strcat` 没有限长，接收缓冲区又没有在完成分支显式补 `\0`。当前短消息现象正常，不等于任意长消息都安全。若计数变量正确初始化，固定的 `Hello!` 加最多10位十进制数、回车换行及结束符共需19字节，能放进 `text[20]`；这只是固定消息格式的容量分析。
3. 本例只有一条已完成消息的缓冲位置。bit15=1 而主循环尚未处理时，新字节被忽略；不能把它当成不会丢数据的通用队列。
4. 主循环先把 `STA` 清零再清缓冲区；若有不受当前发送节奏约束的新数据到来，可能与清缓冲区操作重叠。需要面向更复杂场景设计缓冲交接，而不只是增加固定延时。
5. 三组 `STA` 的声明没有使用 `volatile`；中断与主循环共享状态时，应注意编译器优化与访问可见性。`volatile` 也不能代替缓冲交接或临界区设计。

这些是阅读代码发现的适用边界，不是本次已经观察到的实验故障，也不取消基础实验的完成状态。旧构建产物随工程保留，仅作为原文件，不作为本次重新编译通过的证据。
