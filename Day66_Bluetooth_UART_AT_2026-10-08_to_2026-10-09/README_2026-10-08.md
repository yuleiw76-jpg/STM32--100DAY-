## 2. 对 STM32 来说，模块仍是 UART 设备

STM32 通过 UART 把字节交给蓝牙模块；无线连接与无线数据传递由模块处理。这里不要求 STM32 自己实现蓝牙无线协议。

两条正常通信路径：

```text
按键 -> EXTI 服务函数 -> USART1 TX -> 模块 RX -> 无线链路 -> 手机应用
手机应用 -> 无线链路 -> 模块 TX -> USART1 RX -> 接收状态机 -> 命令比较 -> LED
```

这是代码与手册的预期路径，尚非本人的蓝牙实测结果。115200 是本例 STM32 与模块之间的 UART 波特率，不是要求在手机上把无线速率设置成 115200。

## 3. AT 配置与手机通信是不同阶段

| 阶段 | 对端与链路 | 本节参数及用途 |
| --- | --- | --- |
| 固定 AT 配置模式 | 电脑 -> USB 转 TTL -> 模块 UART | 手册使用 38400、8N1，查询或设置模块参数；示例中 STM32 仅供电 |
| 正常通信模式 | STM32 UART <-> 模块 <-> 手机 | 模块的通信 UART 设为 115200、8N1，与 `uart_init(115200)` 一致 |

本节重点命令：`AT` 测试应答、`AT+RESET` 模块复位、`AT+UART?` 查询串口参数、`AT+UART=115200,0,0` 设置波特率/停止位/校验。后两项中的 `0,0` 表示 1 位停止位、无校验，不是“0 位停止位”。命令与响应都只是学习示例，今日没有实际发送。

在手册所用的固定 38400 AT 模式下，设置正常 UART 为 115200 后，继续发送 AT 查询仍使用 38400；退出 AT 模式、按正常通信方式工作时才使用已配置的 UART 参数。用户最初混淆了两个阶段，随后已正确区分。

补充知识：厂家资料同时描述了固定 38400 和使用模块自身 UART 波特率的 AT 进入方式，因此不能说“所有 HC-05 的所有 AT 模式都是 38400”。具体 KEY/PIO11/EN 引脚和上电步骤，以实际板型、固件及说明书为准。[汇承 HC-05 AT 指令 V2.1，第3、7页](https://www.hc01.com/downloads/HC-05AT.pdf)

### 到货后接线核对表（尚未接线验证）

| AT 配置 | UART 数据 | USB-TTL TX -> 模块 RX；USB-TTL RX <- 模块 TX |

## 5. 字符串发送：指针、终止符与 TXE

发送函数的外层 `while(*Data)` 逐个处理字符；`USART_SendData(USART1, *Data++)` 交出当前字符并前移指针；内层空循环等待 TXE 置位后继续。结尾的 NUL 不发送。[发送函数源码](Code/HC05/SYSTEM/usart/usart.c)

### 指针与字符内容不能混淆

- `Data` 是地址；`*Data` 是该地址处的字符。
- `*Data++` 等价于 `*(Data++)`，不是把字符值加一。
- 补充纠正手册的时序表述：递增副作用在实参求值过程中、进入 `USART_SendData` 函数前完成，不是等这个函数执行完后才递增。
- 字符数字 `'0'` 的值不是零；`' '` 是空格，也不是结束符；`'\0'` 才是值为零的 NUL 字符，不是空地址。
- `"0A"` 的循环体执行两次，第三次条件判断读到 NUL 后退出，并没有执行第三次循环体。[C 委员会草案 N843，§6.5.2.2、§6.5.2.4、§7.1.1](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n843.htm)

### 同一个数组还需要有效的结束符

```c
char a[] = {'a', 'b'};        // 只有2个元素，没有自动追加 NUL
char b[] = "ab";              // 3个元素：'a'、'b'、'\0'
char c[] = {'a', 'b', '\0'};  // 明确包含结束符
```

第一种不能交给本例的字符串发送函数期待它自动停止；发完两个字符后继续读取就越过数组范围。课堂中“数组连续，所以读完后面必然是零”的理解已纠正。正确字符串必须在有效对象范围内包含结束符。[C 委员会草案 N843，§6.5.6、§6.7.8](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n843.htm)

补充纠正手册：两个独立的 `char a='a'; char b=0;` 不保证相邻，也不因此组成合法字符串。把 `&a` 传入这个一直向后读的函数仍不可靠。当前 `exti.c` 中相关 a/b 定义和 `UART1_Send_String(&a)` 均已注释，本次没有执行该不安全实验，也没有改写原程序。

### TXE 不等于整帧发送完成

- TXE：发送数据寄存器空，当前数据已移入移位寄存器，可以准备下一个字节。
- TC：数据帧发送完成；不能把 TXE 当成 TC。
- 本函数是在轮询 TXE，没有因为读取这个标志就开启发送中断。
- 本函数返回时，不保证最后一个字符已完整从 TX 引脚发完；更不能据此证明手机已成功收到。[ST RM0008，§27.6.1](https://www.st.com/resource/en/reference_manual/rm0008-stm32f103xx-advanced-armbased-32bit-mcus-stmicroelectronics.pdf)

## 6. 接收完整命令，再决定是否翻转 LED

`USART_RX_STA` 的低14位记录有效字节数，bit14 表示收到 CR，bit15 表示完整消息已到。收到 `\r` 后，例程要求下一字节为 `\n` 才判定完成；CR/LF 都不存入 BUF。这是例程约定的报文结束方式，不是蓝牙本身要求每条数据必须有 CRLF。

接收完成后比较 `strcmp((char*)USART_RX_BUF, "q") == 0`：两个字符串相同返回零，不同返回非零，非零不保证一定等于 1。[C 委员会草案 N843，§7.21.4.2](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n843.htm)

在缓冲区已清零、帧未写满的正常路径下，代码推演如下（均未实测）：

| 输入 | 接收状态与预期处理 |
| --- | --- |
| `q`，没有 CRLF | 尚未判定消息完成，不执行命令比较，不翻转 LED |
| `q\r\n` | 完整消息，BUF 内容是 `"q"`；匹配后翻转 PC13 |
| `qq\r\n` | 完整消息，但 `"qq"` 不等于 `"q"`；不翻转 LED |
| `Q\r\n` 或 `q \r\n` | 与小写、无额外字符的 `"q"` 不完全相同；不翻转 LED |

是否匹配都不影响后续完整帧的清理：`memset` 清 BUF，STA 重置为零，为下一条消息做准备。LED 是状态翻转，不代表程序会自动亮一下再恢复。

`\r\n` 是线路上的报文结束标记；`'\0'` 是内存里的字符串结束符。当前短帧的 NUL 来自缓冲区初始零值或上一完整帧后的清零，并不是接收程序把 CRLF 转成了 NUL。

## 7. 原例程已知边界与待验证点

以下是只读源码检查或机制推演，不是今日发生的实测异常，也没有在本次修复。

| 检查点 | 源码事实、推演与后续动作 |
| --- | --- |
| NUL 终止 | `usart.c` 完成帧时没有显式写 `BUF[len]='\0'`。正常短帧依赖已有零，不能宣称每帧都保证正确终止；后续应明确保留终止符空间 |
| 错帧恢复 | CR 后不是 LF，以及长度溢出分支只清 STA、不清 BUF。旧后缀可能污染下一条短帧；例如 `abc\rX` 后再收 `q\r\n`，按代码推演可能比较到 `qbc` |
| 满缓冲区 | BUF 为200字节；第200个普通载荷字节写入后状态便复位。不能写成已支持200字节有效载荷，更不能把溢出后的 strcmp 当安全读取 |
| 中断占用 | EXTI 抢占优先级2，USART1为3；按键服务中延时10ms并阻塞发送，可能拖延连续串口接收、增加溢出风险，尚无压力实测 |
| AFIO/JTAG 顺序 | `KEY_Init` 在仅开启 GPIOB 时钟后配置关闭 JTAG，AFIO 显式开启在后调用的 `EXTIX_Init`。顺序需在后续独立上电测试中核验；不能写成已证实故障或可省略 AFIO 时钟 |
| 注释与实现 | `usart.h` 的“末字节为换行符”注释与当前 CR/LF 不入 BUF 的实现不一致；笔记以实现为准 |

后续修复或诊断时应保留原快照、在另一个副本中单项修改并验证。本次未修改代码，未因这些静态风险追加不存在的实验结果。
