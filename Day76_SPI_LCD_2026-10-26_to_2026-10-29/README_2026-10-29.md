## 归档版本与Hello照片为何不同

交接曾将测试描述为“暂停循环RGB”。只读检查发现磁盘main.c仍保留RGB快填屏循环，随后本人明确澄清：**是在调试时暂停循环，源码没有改。**

当前源码初始化后先蓝色填屏、显示Hello，随后进入仍启用的红绿蓝循环：

```c
LCD_Fill_fast(0, 0, LCD_W, LCD_H, BLUE);
LCD_ShowString(0, 40, (const uint8_t *)"Hello",
               WHITE, BLUE, 16, 0);
```

上面是实际主函数中的测试调用摘录。照片记录调试暂停时的显示；继续运行后，后续RGB填屏会覆盖文字。因此本包**不是持续静止显示Hello的版本**。收尾按本人确认保留源码，没有替本人注释循环。

Hello本次验证参数：坐标(0,40)，16号字、WHITE前景、BLUE背景、mode=0非叠加。不能推广为所有字号、叠加模式、单独绘点或触摸均已验证。

## 分块发送的计算与口头自测

| 内容 | 本次理解与计算 |
| --- | --- |
| 像素数 | 480×320=153600像素 |
| 整屏像素数据 | 153600×2=307200字节=300KiB，窗口命令等另计 |
| 缓冲大小 | 128像素×2字节=256字节 |
| 整屏批次 | 153600÷128=1200次像素数据批量发送 |
| 减少了什么 | 减少发送函数调用次数，像素数据总量不变；1200不是提速倍数 |
| 缓冲下标 | 每个像素按高、低两字节成对填入，下标每次加2 |
| 末批算例 | 剩20像素时发40字节；这是口头算例，不是已做过20像素尾批实测 |
| 剩余量 | total_pixels减本批像素数，前后保持像素单位 |

最初口头把“两字节”说成“两位”，经讨论已纠正。本次全屏像素数恰好整除128，不能据全屏成功声称所有非整批边界均实测通过。

## 字符串与颜色理解

- p++移到下一个字符；横坐标按sizey/2前进；遇到第一个'\0'结束。
- fc是文字颜色，bc是背景颜色。曾将白字蓝底的背景回答为RED，纠正后明确为WHITE、BLUE。
- DrawPoint、ShowChar、ShowString均已移植；Hello非叠加模式的显示结果不等同于绘点函数每条分支都单独测试。

## 栈与启动文件：理解范围

- 讨论了局部缓冲通常使用SRAM中的栈空间，局部变量也可能因编译安排使用寄存器。
- 当前Stack_Size EQU 0x400预留1024字节；本例buffer为256字节，函数调用与其他栈使用也须计入。
- 2KiB局部数组本身已超过1KiB预留栈，不能仅根据芯片总SRAM有20KiB判断可用。
- 函数返回时通常恢复栈指针、允许空间复用，不保证把旧内容清零。
- EQU用于定义常量，SPACE预留空间。
- **没有修改Stack_Size，没有做栈溢出实验，也没有测量栈峰值或证明最坏情况裕量。**

理解上述概念即可作为本节栈基础部分的收束，不额外要求执行溢出实验。
