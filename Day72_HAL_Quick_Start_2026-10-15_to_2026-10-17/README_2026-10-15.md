## 4. GPIO与时钟复习

PC13使用推挽输出、无上下拉、LOW速度。日结时gpio.c已经是LOW，不沿用白天曾显示HIGH的旧状态，也没有为归档再改源工程。

应用逻辑为：

```c
HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, GPIO_PIN_RESET);
HAL_Delay(800);
HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, GPIO_PIN_SET);
HAL_Delay(800);
```

本板LED低电平点亮，因此RESET亮、SET灭。亮灭取决于LED电路接法，不取决于“上拉还是下拉”。两段延时合计标称1600ms；没有独立测量精确闪烁周期。

当前主时钟路径是HSE按8MHz使用、PLL乘9、SYSCLK/HCLK为72MHz。APB1分频2得到PCLK1=36MHz，对应TIM3/TIM4输入时钟为72MHz；APB2分频1，PCLK2=72MHz。

用户曾把定时器Internal Clock理解成必须使用HSI，已解释：这里是从芯片内部时钟树取时钟，系统主时钟仍可来自HSE和PLL。对本例F103，APB预分频为1时定时器时钟=PCLK，否则=2×PCLK；该分频和定时器PSC是不同层次。

## 5. TIM3四路PWM

### 最终参数与计算

| 项目 | 当前配置/按配置计算 |
| --- | --- |
| 定时器 | TIM3；不是手册示例TIM4 |
| 定时器输入时钟 | 72MHz |
| PSC | 72−1=71，计数频率1MHz |
| ARR | 20000−1=19999，计数0～19999 |
| PWM周期/频率 | 20000×1μs=20ms；50Hz，均为按配置计算 |
| 模式与极性 | 向上计数、PWM mode 1、High |
| CH1/PA6 | CCR1=5000，目标占空比25% |
| CH2/PA7 | CCR2=10000，目标占空比50% |
| CH3/PB0 | CCR3=15000，目标占空比75% |
| CH4/PB1 | CCR4=19000，目标占空比95% |

```text
fCNT = fTIM / (PSC + 1)
fPWM = fTIM / [(PSC + 1) × (ARR + 1)]
高电平占空比 = CCR / (ARR + 1)   （本例向上计数、PWM1、High）
```

四个通道共用PSC、ARR和CNT，所以频率相同；CCR分别决定脉宽，不能说PWM频率与ARR无关。

### 学过的细节与修正

- ARR预装载控制新ARR什么时候生效，不是“是否自动把CNT归零”。CNT到边界正常回绕不依赖开启ARPE。
- CCR预装载开启时，新CCR通常在下一次更新事件装入活动寄存器，避免在当前周期中途改变脉宽。
- Pulse是初始CCR值，不是百分比。15000/20000是3/4，不是1/3。
- PWM1在本例CNT<CCR时输出高，PWM2反过来。CCR=0时可以是恒低/恒高，不能只凭没有边沿断言定时器没有运行。
- Fast Mode用于特定触发响应，不是提高普通连续PWM频率的开关，不照抄“一律开启”。
- PC13没有所需定时器通道功能，不能直接当本例硬件PWM输出；本例选择PA6、PA7、PB0、PB1。
- MX_TIM3_Init只初始化；HAL_TIM_PWM_Start要手动为各通道调用。启动后由硬件持续产生PWM，主循环HAL_Delay不会暂停定时器。

### 调试记录：下载后未看到预期波形

1. **现象**：用户探头接PA6/PA7/PB0/PB1，对应逻辑分析仪0/1/2/3，已共地，但没有预期连续PWM。
2. **假设与测试**：检查所选定时器、实际引脚、启动调用、PSC/ARR与CCR范围，而不是仅根据软件中SCL/SDA旧名字判断。
3. **观察A**：白天读取tim.c时，Period曾为2000−1，而CCR为5000/10000/15000/19000。对PWM1/High，CCR都超过计数范围，可造成恒高、看不到预期边沿。
4. **修改A**：指导把ARR改为20000−1，重新生成、重载、构建和下载。
5. **观察/修改B**：用户后来明确说设置CCR时误用了TIM4，而实际PWM启动对象是TIM3；纠正后出现波形。这是用户对最终修正的报告，不与另一时刻磁盘代码强行矛盾化。
6. **验证**：用户提供143605四路连续波形并明确确认正确，接受该验证，不再强制补游标测量。当前保存代码已统一为TIM3，ARR=19999。

50Hz和25%/50%/75%/95%是源码目标值；截图视觉与目标趋势一致，但没有记录独立精密测量数值。午后的PWM验证不自动证明晚间加入的编码器功能也已运行成功。

## 6. TIM4编码器模式

### 当前配置与为什么这样设置

| 项目 | 当前配置与含义 |
| --- | --- |
| 引脚 | PB6=TIM4_CH1，PB7=TIM4_CH2；是输入，不是PWM输出 |
| Combined Channels | Encoder Mode |
| Encoder Mode | TI1 and TI2，两路参与四倍频译码 |
| PSC | 0，不分频，保留有效计数事件 |
| Counter Mode | 配置显示Up，但编码器运行时加减方向由A/B关系决定 |
| ARR | 4000−1=3999，CNT在0～3999间回绕；不等于所有编码器一圈固定4000次 |
| CKD | No Division，涉及滤波等采样时钟，不与PSC混同 |
| ARR preload | Disable；本例ARR固定，并非控制能否回绕 |
| 输入极性 | 两路Rising配置对应不反相；不能据此说四倍频译码只数上升沿 |
| IC Selection | Direct，两路分别使用自己的输入 |
| IC Prescaler | No Division；不作为二倍频/四倍频选择开关 |
| Input Filter | 两路均为1，轻度数字滤波；不是1ms，也不保证消除机械抖动 |
| GPIO电气配置 | 当前源码为GPIO_MODE_INPUT、GPIO_NOPULL；未接信号源时不把随机变化当作有效结果 |
| NVIC | 分组4，TIM4抢占优先级5、子优先级0；5是本例选择，不是TIM4固有要求 |

CNT由编码器的有效变化推动，而不是因内部72MHz时钟持续自由计数。稳定且没有有效变化的A/B输入不会使CNT连续增加。用户最初对0减计数答成1，随后解释了下溢0→3999；之后正确回答上溢3999→0。

用户最初认为每次计数都必须进入中断，已纠正：定时器硬件自动改CNT。软件若要累计越过ARR/0的次数，才需要相应更新中断处理。这个区分仍值得下次短时复习。

### 已保存的启动代码

在MX_TIM4_Init之后、USER CODE BEGIN 2内，当前main.c存在：

```c
HAL_TIM_Encoder_Start_IT(&htim4, TIM_CHANNEL_ALL);
__HAL_TIM_ENABLE_IT(&htim4, TIM_IT_UPDATE);
```

第一句启动编码器CH1/CH2并使能对应CC捕获中断；这里TIM_CHANNEL_ALL不是把CH1～CH4全部当编码器通道。第二句另外开启更新中断源。不能把Start_IT当作已经自动开启更新中断。

局部TIM4 NVIC页面一度不能修改抢占优先级，指导到System Core→NVIC全局页面检查；最终保存的.ioc和tim.c均为5,0。没有独立证明此前UI不可编辑的唯一触发原因。

### 弱回调与真正的中断入口

作者在main.c实现的是HAL_TIM_PeriodElapsedCallback更新回调，不是重新定义TIM4_IRQHandler。当前生成的中断入口位于stm32f1xx_it.c，并调用HAL_TIM_IRQHandler(&htim4)。HAL处理相应中断标志，再调用更新回调。

```text
TIM4_IRQHandler → HAL_TIM_IRQHandler → HAL_TIM_PeriodElapsedCallback
```

库里默认更新回调为弱定义。用户提供同签名、不带__weak的普通定义时，链接器使用用户强定义覆盖默认弱定义；不是运行时修改HAL库文件。用户确认理解这一作用，并决定不复刻作者的溢出累计回调。

因此当前快照没有用户自己的Encoder_Overflow_count或更新回调实现。即使更新中断被使能，也不会凭空得到软件累计溢出次数。未来若做累计计数，再补回调、初始更新标志处理及边界验证。
